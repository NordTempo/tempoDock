# Upgrading from 0.14 or 0.23 to the latest (0.24.1)

How to update a control plane on v0.14.x or v0.23.x to v0.24.x, what
changes on the way, and how to get back if it goes wrong. Each path was
tested end to end on a throwaway server with `e2e/upgrade/run.sh FROM TO`:

| Path | Result |
|---|---|
| v0.23.0 to v0.24.1 | pass, 10 s |
| v0.23.0 to v0.24.0 | pass, 13 s |
| v0.14.2 to v0.24.0 | pass, 8 s |

None of the updates lost anything. Read
[Volumeless databases](#volumeless-databases-79) first: that is the one
change that can cost data, and it hits on the first restart after the
update, not during the update itself. #113 fixes it.

## Before

1. **Find services that keep data without a Dock volume.** A service whose
   image declares a `VOLUME` (Postgres, MySQL, Redis, MongoDB, ...) but has
   no Dock volume keeps its data in an anonymous Docker volume. Since v0.19.0
   (#79) Dock removes a container's anonymous volumes along with the
   container, so **the first restart, redeploy or stop and start after the
   update starts that service empty, and the old data is deleted from
   disk**. List them on the server:

   ```sh
   for c in $(sudo docker ps -q --filter label=dock.managed=true); do
     sudo docker inspect "$c" -f '{{.Name}}{{range .Mounts}} {{.Name}}:{{.Destination}}{{end}}'
   done | grep -E ' [0-9a-f]{64}:'
   ```

   Each line is a container and the anonymous volume it keeps data in.
   For each one: dump its data (`pg_dump`, `redis-cli save` and a copy, ...),
   add a Dock volume at the same path (`dock volume add data /var/lib/postgresql/data`)
   and restore the dump into it after the redeploy. Template databases
   (`dock service create --template`) have a Dock volume and are not
   affected.
2. **Back up the control plane.** The updater writes a backup itself
   (`/var/lib/dock-update/backup-<version>-<time>.tar.gz`), but keep one of
   your own off the server: `sudo dock admin backup -o /root/dock-pre-update.tar.gz`.
3. **Updater token.** The repository is private:
   `/etc/dock/github-token` (root:dock, 0640) must hold a token that can
   read its releases. `dock update` shows the newer releases when it works.
4. **Check the disk.** The update stages about 60 MB in
   `/var/lib/dock/update/` and `/var/lib/dock-update/`, plus the backup.

## Update

From any machine with a CLI logged in as an operator:

```sh
dock update                 # what's new
dock update apply v0.24.1   # waits until the control plane runs it
```

`apply` waits by default (`--detach` returns at once). There is no
`--wait` flag. Apps and routing keep running. The API is down for a few
seconds. The new daemon doesn't recreate any app container when it
starts: the same containers keep running on their old release.
Afterwards, install the matching CLI (`dock version` tells you).

## What changes

### Database (migrations 0037 to 0053)

v0.14 is at migration 36, v0.23 at 51, and v0.24 at 53. All run on the
first start and only go forward. In the tests, `PRAGMA integrity_check` was
`ok`, `foreign_key_check` was empty and no table lost a row.

| Migration | What |
|---|---|
| 0037 | Analytics sites get a public slug; duplicate public dashboard domains are dropped from all but the oldest site |
| 0038 | `ensure_running` |
| 0039 | GitHub deliveries keep a body hash (replays are refused) |
| 0040 | `install.secrets_format` (see below) |
| 0041 | `domains` is rebuilt for verification (see below) |
| 0042 | Health check settings per service (0: the default) |
| 0043 | Indexes for sessions and finished releases |
| 0044 | Environment lock, and the org setting "lock new production environments" (off) |
| 0045 | Pre-deploy command (empty) |
| 0046 | Release logs kept past their container |
| 0047 | Access requests (agents asking for blocked actions) |
| 0048 | Volume snapshots |
| 0049 | One-off and scheduled runs |
| 0050 | Held deploys into locked environments |
| 0051 | Staged services and domains (`dock apply FILE`, Compose import) |
| 0052 | Stopped services |
| 0053 | Log drains |

### Sealed values are resealed (ADR 0041)

Values sealed at rest (variables, org variables, release configs,
storage, git, Cloudflare and alert channel credentials, ...) are bound to
their row on the first start: `install.secrets_format` goes from 1 to 2 and
every value is rewritten in format 2. Nothing for you to do. Every variable
revealed the same value afterwards, new releases got them, and backups
still opened the storage connection's keys. Watch the log for "doesn't
open": a value listed there must be set again. **An older binary can't read
format 2**, so going back needs the pre-update database (below).

### Custom domains are verified (ADR 0042)

Every existing domain is marked verified as of when it was added, so it
keeps routing (tested: same status, same routes through Caddy). A custom
domain added **after** the update by an org admin or a non-operator token
waits for `TXT _dock-challenge.<hostname>` = `dock-verify=<token>` and doesn't
route until then. `dock domain list` shows the record. Domains an operator
adds, and names under the base domain, are verified when added.

### Ongoing health checks (ADR 0043)

From the next release of each service (not at the update), Docker probes
it every 30 s: `GET` on its health check path, or TCP on its port.
Template databases are probed over TCP, and a service without a port gets
no check. A service that fails 3 probes in a row is restarted in place,
with backoff, and raises an `unhealthy` alert. A service whose health
check path is wrong now gets restarted, where before it only failed its
deploy. Turn it off per service with an interval of `-1` (`off` in
`dock.toml`).

### Off until you turn them on

The environment lock and "lock new production environments" (ADR 0044),
pre-deploy commands, log drains, volume snapshots, scheduled runs and
stop/start all start out off or empty. Tokens, `dock login` tokens and
browser sessions keep working, and nobody is locked out.

## Volumeless databases (#79)

Measured on every path above (v0.24.0 and v0.24.1 behave alike), for
`postgres:17-alpine` without a Dock volume:

| When | Data |
|---|---|
| The update itself | kept (same container, same anonymous volume) |
| First `dock restart`, redeploy or stop and start after it | **gone**: a new empty anonymous volume, and the old one is deleted |
| The same on v0.14.2 | also a new empty anonymous volume per container, but the old volume stayed on disk and could be copied back by hand |

This comes from #79 (v0.19.0), which removes a container's anonymous volumes
along with it, so they stop leaking disk. #113 (ADR 0052) fixes it: a
container that went live keeps its anonymous volumes when it is removed,
with one kept copy per service, and volumes made before the fix are never
removed. A deploy then warns when no volume covers a path where the image
keeps data. Until the server runs a release with #113, do step 1 of
[Before](#before) for every such service before you restart it, and assume
a restart loses the data. Even with the fix, each new release starts that
service empty: add a Dock volume.

## Rollback

**Automatic.** If `install.sh` fails, or the new version doesn't answer
on the API within 90 s, the updater stops `dock`, puts back the saved
binary, units and `caddy.json` from `/var/lib/dock-update/previous/` and
the database from the pre-update backup, then starts the old version. Only
changes made in those seconds are lost. `dock update` shows the result, and
`journalctl -u dock-update` has the full log. Tested with a fake release
whose daemon never comes up: see `e2e/upgrade/server/failed-update.sh`.

**By hand**, after the new version has run for a while (as root on the
control plane):

```sh
systemctl stop dock
install -m 0755 /var/lib/dock-update/previous/dock /usr/local/bin/dock
cp /var/lib/dock-update/previous/units/* /etc/systemd/system/
cp /var/lib/dock-update/previous/caddy.json /etc/dock/caddy.json
systemctl daemon-reload
mkdir /root/restore && tar -xzf /var/lib/dock-update/backup-*.tar.gz -C /root/restore
rm -f /var/lib/dock/dock.db-wal /var/lib/dock/dock.db-shm
install -m 0600 -o dock -g dock "$(find /root/restore -name dock.db)" /var/lib/dock/dock.db
systemctl start dock
```

The old version comes back with its data as of the update. Tested from
v0.24.0 to v0.14.2: version, migrations, variables (format 1 again), tokens
and the browser session were all back. Everything done after the update is
lost: releases, variables, domains, backups in the list (their snapshots
stay in the repository).

**Then clean up services deployed after the update.** The restored database
doesn't know their newer containers. Those keep running unmanaged, and the
log says `drift: N containers are not part of any active release`. Their
routes return 502, and a redeploy fails with "container name ... is already
in use" or "driver failed programming external connectivity", because
the old database hands out the same release numbers and ports again.
Remove the containers that the drift line names, then redeploy each of
those services:

```sh
journalctl -u dock | grep 'drift:' | tail -1
docker rm -f dock_p1_e1_s3_r2 ...        # the names from that line
dock restart -p <project> -e <env> -s <service>
```

## After

- `dock update` shows `last update ... succeeded`, and `dock version` shows
  the CLI and server in step.
- `journalctl -u dock | grep -i "open"` shows nothing about sealed values.
- `dock domain list` in each environment: every existing domain is still
  `active`.
- Redeploy one service per environment and check that it goes live.
- Fix any volumeless database before its next restart (above).
