Container terminal

ADR 0107. A shell inside the service's running container (the web side of dock exec). Every mock shows the same state: web in shop/production, release r42 running, a session open in its container. The terminal is xterm.js, loaded only when it opens, cursor not blinking. Admins on the environment only; each session is in the audit log as service.exec, and closing the page ends it.

A. Its own tab, Shell, between Jobs and Data

Operating group grows to Jobs, Shell, Data, Variables. The tab is the terminal: one line of what it is attached to, then the terminal to the bottom of the window. Nothing connects until you press Connect (or Enter), so opening the tab by accident starts nothing.

B. A view inside Jobs: Commands, Scheduled, Shell

No new tab. Jobs already holds "run something in this service" (one-off commands, scheduled jobs), so the shell is its third view, underlined like Requests' views. The line under the views says how it differs from a command.

C. A drawer under the page, opened from ···

··· gets "Open shell" in its connect group (key g s). The terminal docks at the bottom of the service page and stays open while you move between the service's tabs, so Logs or Metrics sit above what you type. Drag the line to resize; up to three sessions as small tabs. Leaving the service closes it.

Locked or not allowed

Same in every mock. Not an admin on the environment: the tab, view or menu item isn't shown. A locked environment holds tokens, not your UI session, so the UI connects; the public demo shows the place and refuses to connect.

The demo is view-only: shells into containers are off here. dock exec opens one on your own Dock.

Pick one: A (its own tab), B (a view in Jobs) or C (a drawer across the service's tabs). My lean is A: one place, one key, the simplest to build and the clearest about when a session is open.
